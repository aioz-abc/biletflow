# Нурсат — третий этап, отчёт к 15 октября

Подготовлено 15 октября 2026 года. Ветка реализации: `codex/nursat-phase3`
(от `dev`, после PR #10 и admin shell Мирата).

Базовая цепочка «резерв → симуляция оплаты → QR-билет → check-in» уже была
показана во втором отчёте. На этом этапе закрыты требования SRS 4.3–4.7 по
билетам и оплате, которых в MVP ещё не было, и добавлены демо-данные для
всей команды.

## Результат

- **Письмо с подтверждением заказа и QR-билетами (SRS 4.4, 4.7).** После
  успешного checkout — платного или бесплатного — покупатель получает письмо:
  событие, дата, площадка, сумма с пометкой «симуляция», идентификаторы всех
  билетов, ссылка на билеты в аккаунте и отдельный SVG-файл с QR для каждого
  билета. Письмо отправляется через `transaction.on_commit`, то есть только
  после фиксации транзакции: откатившийся checkout письма не порождает.
  Неудачная оплата и повторный checkout уже подтверждённого заказа писем не
  отправляют. Локально письмо видно в `docker compose logs web`.
- **Счётчики по типу билета (SRS 4.3).** `GET /events/{id}/ticket-types`
  теперь возвращает для организатора и platform admin поле `stats`:
  quantity, available, reserved (живые резервы), sold, checked_in, refunded,
  cancelled. Посетителям и анонимам приходит `stats: null` — продажи
  организатора не раскрываются.
- **Сервисный сбор и сводка продаж (SRS 4.6).** У `Payment` появилось поле
  `fee_minor` — симулированный сбор платформы (`PROCESSING_FEE_BPS`, по
  умолчанию 3%). Покупатель платит сумму заказа, сбор удерживается из выплаты
  организатору, поэтому суммы заказов и фронтенд не меняются. Новый эндпоинт
  `GET /events/{id}/sales` показывает организатору gross, скидки, возвраты,
  сборы, ожидаемую выплату и разбивку по типам билетов. В ответе всегда есть
  `simulated: true` — по SRS демо-платежи нельзя выдавать за настоящие.
  Миграция `0005_payment_fee` заполняет сбор для уже существующих платежей.
- **Команда `seed_demo`.** `python manage.py seed_demo` создаёт организатора,
  посетителя с билетами, Event Admin для check-in и platform admin, три
  события (платное с двумя тарифами, бесплатное, unlisted), промокод `DEMO10`
  и два оформленных заказа. Заказы проходят через настоящие `reserve`/`checkout`,
  поэтому данные подчиняются всем правилам инвентаря и цен. Повторный запуск
  ничего не дублирует; без DEBUG команда требует `--password`.
- `demo_mvp.py` дополнительно проверяет счётчики и сводку продаж через HTTP.

## Командная интеграция

- Фронтенд (Анвар, Мират) может сразу показывать организатору статистику
  по тарифам и страницу продаж — контракт и примеры JSON в
  [BACKEND_MVP_API.md](BACKEND_MVP_API.md).
- `seed_demo` даёт всем одинаковые аккаунты и события: Абылаю — Event Admin
  `demo-staff@biletflow.local` и билеты для проверки сканера, Мирату —
  `demo-admin@biletflow.local` для админки и `DEMO10` для экрана кампаний.
- Обновлены `BACKEND_MVP_API.md`, `DATA_MODEL.md` и README.

## Проверка

```sh
python manage.py check
python manage.py makemigrations --check --dry-run
python manage.py test --noinput
ruff check . && ruff format --check .
python manage.py seed_demo   # дважды: второй запуск ничего не создаёт
python demo_mvp.py           # против запущенного сервера
```

Полный набор: **65 тестов** (было 57), все проходят на PostgreSQL 16.
Новые тесты (`ticketing/test_phase3.py`) проверяют: письмо с вложениями QR
для платного и бесплатного заказа; отсутствие письма при неудачной и
повторной оплате; точные значения `stats` после резерва, покупки, check-in и
возврата; скрытие `stats` от посетителя и анонима; расчёт gross, сборов,
возвратов и выплаты; доступ к сводке только владельцу; повторяемость
`seed_demo` и запрет пароля по умолчанию вне DEBUG. Ruff и проверка
миграций — без замечаний. `demo_mvp.py` по HTTP: заказ 2 500 KZT, сбор 75 KZT,
ожидаемая выплата 2 425 KZT, повторный check-in отклонён.

## Демо 15 октября

1. `docker compose up --build -d --wait`, затем
   `docker compose exec -T web python manage.py seed_demo` — показать список
   аккаунтов и событий.
2. Войти как `demo-attendee@biletflow.local`, купить билет на Jazz Night с
   промокодом `DEMO10`. В `docker compose logs web` показать письмо с
   билетами и QR-вложениями.
3. Войти как `demo-organizer@biletflow.local`: `GET /api/events/{id}/ticket-types`
   — счётчики sold/reserved/checked_in; `GET /api/events/{id}/sales` — gross,
   скидка, сбор 3% и ожидаемая выплата.
4. Сделать check-in билета как `demo-staff@biletflow.local`, затем возврат
   другого заказа организатором — показать, как меняются `stats` и сводка.
5. `docker compose exec -T web python demo_mvp.py` — весь путь одной командой.
