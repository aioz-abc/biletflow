# Подключение frontend к BiletFlow

Инструкция для разработчика React frontend. Сверена с реализацией backend MVP
13 сентября 2026 года. Полный контракт: [BACKEND_MVP_API.md](BACKEND_MVP_API.md).
Старый `API_CONTRACT.md` — исторический проект API; не использовать его
плановые endpoint'ы как уже работающие.

## 1. Что строим

Один React frontend в существующей папке `frontend/` обслуживает посетителя
и организатора. Основной сценарий:

1. Организатор регистрируется, создаёт событие и типы билетов, публикует событие.
2. Посетитель открывает событие, входит, выбирает билеты и создаёт заказ.
3. Посетитель подтверждает тестовую оплату и получает QR-билет.
4. Организатор сканирует QR и отмечает проход.

В проекте уже установлены React, Vite и Tailwind. Роутер и библиотека камеры
пока не установлены. Приведённые ниже адреса экранов — предложение для frontend,
а адреса `/api/...` — реально реализованные backend routes.

## 2. Локальный запуск и соединение

Из корня репозитория:

```sh
docker compose up --build -d --wait
```

В другом терминале:

```sh
cd frontend
npm ci
npm run dev
```

Backend: `http://127.0.0.1:8000`. Проверка: `GET /api/health` возвращает
`{"status":"ok","database":"ok"}`. Адрес frontend покажет Vite.

В текущем `frontend/vite.config.js` прокси ещё не настроен. При реализации
добавить `server` рядом с существующим `plugins`, сохранив плагины:

```js
server: {
  proxy: {
    '/api': {
      target: 'http://127.0.0.1:8000',
      changeOrigin: true,
    },
  },
},
```

Frontend должен обращаться к относительным `/api/...`. Прямой вызов порта
8000 из браузера с другого origin потребует CORS, которого сейчас нет.
Прокси Vite относится к разработке; для production нужно направить `/api`
через reverse proxy к Django. `vite build` сам такой proxy не создаёт.

У маршрутов нет завершающего `/`. JSON отправлять с
`Content-Type: application/json`. Для защищённых запросов добавлять
`Authorization: Bearer <access>`. Токен не передавать в query string.

## 3. Экраны и запросы

Все API-адреса в таблице указаны без общего префикса `/api`.

| Экран frontend | Запросы | Что отображать / делать |
| --- | --- | --- |
| `/register` | POST `/auth/register` | Тип аккаунта, email, пароль; для организатора профиль |
| `/login` | POST `/auth/login` | Войти, сохранить сессию, вернуться на исходный экран |
| `/events` | GET `/events?page=1` | Опубликованные события, пустой список и пагинация |
| `/events/:id` | GET `/events/:id`, GET `/events/:id/ticket-types` | Описание, даты, место, цены, остатки и выбор количества |
| `/checkout/:orderId` | GET `/orders/:id`, POST `/orders/:id/checkout`, POST `/orders/:id/cancel` | Серверная сумма, срок резерва, результат симуляции |
| `/tickets/:id` | GET `/tickets/:id`, GET `/tickets/:id/qr` | QR, номер, статус; сведения о событии загрузить отдельно |
| `/account` | GET `/me/orders`, GET `/me/tickets` | Свои заказы и билеты, переход к незавершённому заказу |
| `/organizer/events` | GET `/me/events` | Свои события, включая черновики |
| `/organizer/events/new` | POST `/events` | Создать черновик |
| `/organizer/events/:id/edit` | GET/PATCH `/events/:id`, POST `/events/:id/publish` | Изменить поля и отдельно опубликовать/снять с публикации |
| Тарифы внутри редактирования | GET/POST `/events/:id/ticket-types`, PATCH `/ticket-types/:id` | Создать/редактировать/скрыть тип билетов |
| `/organizer/events/:id/attendees` | GET `/events/:id/attendees` | Выданные билеты и статусы прохода |
| `/organizer/check-in` | POST `/tickets/verify`, POST `/tickets/check-in` | Ввод или сканирование QR и подтверждение прохода |

Все списки имеют форму `{count, next, previous, results}`, размер страницы — 20.
Отрисовывать `results`, а не весь объект. Поддержать `?page=2`; фильтры, поиск
и сортировка по произвольным параметрам пока не реализованы. `next` может быть
абсолютным URL backend: не переносить туда Authorization вслепую, использовать
проверенный путь текущего API или самостоятельно увеличивать `page`.

## 4. Регистрация, роли и сессия

Посетитель — `POST /api/auth/register`:

```json
{"email":"visitor@example.com","password":"Choose-a-private-password!"}
```

Организатор:

```json
{
  "email": "host@example.com",
  "password": "Choose-a-private-password!",
  "account_type": "organizer",
  "first_name": "Нурсат",
  "organizer_profile": {
    "display_name": "Student Events",
    "contact_email": "host@example.com",
    "contact_phone": "+77000000000"
  }
}
```

`first_name`, `last_name` и `contact_phone` необязательны. Для организатора
обязательны `display_name` и `contact_email`. Посетитель должен полностью
опустить `organizer_profile`. Регистрация возвращает **201 `{user}` без токенов**:
после неё выполнить отдельный login или показать форму входа.

`POST /api/auth/login` с `{email, password}` возвращает:

```json
{
  "access": "<access JWT>",
  "refresh": "<refresh JWT>",
  "user": {
    "id": 1,
    "email": "host@example.com",
    "first_name": "Нурсат",
    "last_name": "",
    "email_verified": false,
    "roles": ["attendee", "organizer"],
    "organizer_profile": {
      "id": 1,
      "display_name": "Student Events",
      "contact_email": "host@example.com",
      "contact_phone": "+77000000000"
    }
  }
}
```

`GET /api/auth/me` возвращает сам объект пользователя, без обёртки `user`.
Роль проверять через `user.roles.includes('organizer')`: ролей может быть несколько.
`organizer_profile` равен `null` у посетителя. `platform_admin` выдаётся только
административно; отдельной роли `event_admin` в текущем MVP нет.

`event.organizer` — ID **профиля**, а не ID пользователя. Для сравнения владельца
использовать `user.organizer_profile?.id`. Скрытие кнопок не заменяет серверные
проверки: чужие объекты обычно возвращают 404. Email verification сейчас не
реализован и `email_verified: false` не должен блокировать публикацию в UI.

Для первого варианта хранить токены в памяти приложения, например в AuthContext:
после перезагрузки страницы потребуется повторный вход. Хранение долгой сессии
между перезагрузками — отдельное решение; backend пока не устанавливает HttpOnly
auth-cookie. Не подразумевать её наличие и не добавлять сохранение паролей.

Правила общего API-клиента:

1. Access действует 15 минут; refresh — 7 дней.
2. При 401 защищённого запроса один раз вызвать `/auth/refresh` с текущим refresh.
3. Сохранить **оба новых токена**, старый refresh уже использован.
4. Все параллельные запросы должны ожидать один общий refresh Promise. Иначе
   второй refresh получит 401 и может ошибочно завершить рабочую сессию.
5. Повторить исходный запрос максимум один раз. Не запускать refresh для ошибки
   самого login/register/refresh и не зацикливать повторы.
6. При 401 refresh очистить сессию и предложить вход; при сетевом сбое или 429
   показать временную ошибку без бесконечных повторов.
7. Logout: прекратить новые auth-запросы, дождаться текущего refresh, если он есть,
   отправить актуальный refresh на `/auth/logout`, очистить локальную сессию.
   204 не имеет JSON-body. Уже отозванный токен даст 401 — локальный выход всё
   равно выполняется. При смене аккаунта игнорировать поздние ответы старой сессии.

Для публичного каталога токен необязателен. Неверный Bearer-токен может дать 401
даже на публичном endpoint: после завершения сессии убрать этот заголовок.

## 5. Создание события и тарифов

`POST /api/events`:

```json
{
  "title": "Студенческий концерт",
  "description": "Живая музыка",
  "venue": "Алматы, главный зал",
  "starts_at": "2027-01-20T19:00:00+05:00",
  "ends_at": "2027-01-20T21:00:00+05:00",
  "capacity": 100
}
```

Ответ 201 содержит те же поля плюс `id`, `organizer`, `published: false`.
Даты в примере иллюстративные: в форме выбрать будущую дату. `datetime-local`
не содержит timezone; явно определить часовой пояс формы. Если это локальная
зона браузера, конвертировать в ISO перед отправкой и подписать зону рядом с полем.
Если форма обещает время Алматы, не интерпретировать его в произвольной зоне браузера.

Не отправлять весь GET-объект обратно: `id`, `organizer`, `published` read-only
и дадут 400. PATCH содержит только изменяемые поля. Публикация — отдельный
`POST /api/events/:id/publish` с `{"published":true}`.

`POST /api/events/:id/ticket-types`:

```json
{"name":"Стандарт","price_minor":250000,"quantity":100,"max_per_order":5}
```

Дополнительно можно передать `sales_start`, `sales_end` (ISO или `null`) и
`hidden`. Ответ добавляет `id`, `event`, `available`; их не отправлять в PATCH.
Нулевая цена означает бесплатный билет. Для снятия тарифа с продажи отправить
`PATCH /api/ticket-types/:id` с `{"hidden":true}`.

Цены вводить в тенге, перед отправкой переводить в целое число тиын без ошибок
двоичной дробной арифметики. Для отображения `price_minor / 100` форматировать
через `Intl.NumberFormat('ru-KZ', {style: 'currency', currency: 'KZT'})`.
Ограничения полей и диапазоны перечислены в полном контракте.

## 6. Выбор билетов и checkout

Карточка тарифа использует `available`, `max_per_order`, `price_minor` и даты
продаж. Остаток учитывает вместимость всего события: остатки разных тарифов
нельзя складывать как независимые. `available > 0` не означает открытое окно продаж.
Frontend помогает выбрать количество, окончательное решение принимает backend.

По кнопке «Продолжить» вызвать **один** `POST /api/orders`:

```json
{"event":1,"items":[{"ticket_type":1,"quantity":2}]}
```

До покупки требуется вход. После 201 перейти на `/checkout/{order.id}`.
Не создавать заказ при каждом изменении количества и не создавать новый при
перезагрузке checkout. Блокировать кнопку на время отправки. Цены, скидки,
`total_minor` и статус в запрос не передавать — backend отвергнет их.

Пример ответа на создание заказа:

```json
{
  "id": 7,
  "event": 1,
  "status": "pending",
  "total_minor": 500000,
  "currency": "KZT",
  "expires_at": "2027-01-20T12:15:00Z",
  "created_at": "2027-01-20T12:00:00Z",
  "confirmed_at": null,
  "items": [{"ticket_type":1,"quantity":2,"unit_price_minor":250000}],
  "tickets": []
}
```

На checkout показывать сумму **из заказа**, а не текущую цену тарифа. Таймер
строить по `expires_at`; часы пользователя могут отличаться, серверный ответ
окончателен. Резерв действует максимум 15 минут и не дольше начала события.

| Статус | Поведение интерфейса |
| --- | --- |
| `pending` | Доступны тестовая оплата и отмена |
| `confirmed` | Показать выданные билеты; оплату больше не предлагать |
| `expired` | Резерв истёк, предложить вернуться к выбору |
| `cancelled` | Заказ отменён, предложить создать новый |

Оплата: `POST /api/orders/7/checkout` с `{"outcome":"success"}`.
Для теста отказа — `{"outcome":"failure"}`. Оба могут вернуть **200**:
успех определять по `order.status === 'confirmed'`, а не только HTTP-коду.
При отказе остаётся `pending`, билетов нет; можно повторить оплату до истечения
резерва. Бесплатные билеты подтверждаются тем же endpoint с `success`.
Не собирать номер карты, CVV или реальные платёжные данные: это симуляция.

Если ответ checkout потерян, сначала получить `/orders/7`; повторный checkout
того же заказа безопасен и не выпускает лишние билеты. Автоматически повторять
создание заказа после сетевого сбоя нельзя: у `POST /orders` нет idempotency key.
Предложить проверить `/me/orders`, затем явно выбрать дальнейшее действие.

Отмена: `POST /api/orders/7/cancel`, без обязательного body. Отменить можно
неподтверждённый заказ. Отмена оплаченного заказа и возврат сейчас дадут конфликт
либо отсутствуют; не показывать обещание возврата.

## 7. QR-билет и проверка на входе

В подтверждённом заказе `tickets` содержит по одному объекту на каждый билет:

```json
{
  "id": 12,
  "identifier": "4a152457-d9b7-48a6-84ef-552028084cc6",
  "event": 1,
  "ticket_type": 1,
  "status": "valid",
  "issued_at": "2027-01-20T12:01:00Z",
  "checked_in_at": null,
  "qr_token": "<подписанная строка из ответа backend>"
}
```

Backend не вкладывает название/место события в билет. Загружать сведения по
`event`, переиспользуя уже загруженные данные. После снятия события с публикации
покупатель всё ещё видит свой билет, но публичный запрос события может дать 404:
в таком случае показать доступные данные билета и нейтральное сообщение.

`GET /api/tickets/12/qr` возвращает SVG, требует Bearer. Обычный
`<img src="/api/tickets/12/qr">` не добавит этот заголовок. Получить изображение
через авторизованный fetch как Blob, создать `URL.createObjectURL(blob)` и
использовать его в `src`. Освободить object URL при замене/размонтировании.
Не вызывать `.json()` для SVG. Токены и QR не помещать в логи/аналитику.

Для первого экрана check-in достаточно поля вставки `qr_token`; затем добавить
камеру. В строке уже есть подпись — передавать её целиком, не пересобирать QR
из одного UUID и не пытаться самостоятельно определять подлинность.

1. `POST /api/tickets/verify` с `{"qr_token":"<отсканированная строка>"}`.
2. Ответ `{valid: true, ticket: {...}}` позволяет показать найденный билет.
3. По подтверждению отправить тот же payload в `/api/tickets/check-in`.
4. Ответ — сам Ticket с `status: "checked_in"` и `checked_in_at`.

Повторный проход даёт 409; неправильный QR — 400; чужой билет — 404.
Проверка `verify` не резервирует проход: два сканера могут увидеть valid,
но только один check-in завершится успешно. При нескольких кадрах камеры
блокировать параллельную отправку одного скана. После неопределённого сетевого
результата перечитать `verify`, чтобы показать актуальный статус.

Если сканер открыт для конкретного события, сверять `ticket.event` с выбранным
событием перед подтверждением: общий endpoint разрешает владельцу проверять
билеты всех его событий. Камера требует разрешения пользователя и подходящего
браузерного контекста; сохранить ручной ввод как доступный запасной вариант.

`/events/:id/attendees` сейчас возвращает билеты, а не отдельные имена/email
держателей. В UI называть список «Билеты / проходы», не обещать персональный
список гостей, которого в API пока нет.

## 8. Ошибки и состояния интерфейса

| Ситуация | Действие |
| --- | --- |
| Загрузка | Индикатор, кнопки отправки заблокированы |
| Пустой список | Понятный empty state с дальнейшим действием |
| 400 | Ошибки у полей или общее сообщение формы |
| 401 | Однократный refresh для защищённого запроса, затем вход при необходимости |
| 403 | Недостаточно прав для действия |
| 404 | Объект недоступен или отсутствует |
| 409 | Показать причину, обновить заказ/остатки/статус билета |
| 429 | Сообщить об ограничении запросов; учесть Retry-After, если есть |
| Сеть / 5xx | Сообщить о временной проблеме; повтор не должен дублировать покупку |

Ошибки бывают `{detail: "..."}`, `{email: ["..."]}`,
`{non_field_errors: ["..."]}` и вложенные ошибки профиля/items. Не считать любую
ошибку строкой и не завязывать логику на английский текст. Сначала проверять
`response.ok`; `fetch` сам не бросает исключение на 400/500. Для 204 не парсить
JSON. Не вставлять описание события или текст ошибки через сырой HTML.

## 9. Порядок реализации и приёмка

Рекомендуемый порядок: proxy и API-клиент → auth → каталог и событие →
редактор организатора и тарифы → checkout → кабинет и QR → check-in.
Можно использовать обычный fetch; установка Axios/глобального store для
этого сценария не обязательна. Общими сделать управление сессией и обработку API.

- [ ] Посетитель и организатор регистрируются; регистрация не имитирует вход.
- [ ] Login/logout и обновление токенов работают, параллельный refresh не ломает сессию.
- [ ] Организатор создаёт черновик, тариф, публикует событие; посетитель видит его.
- [ ] Посетитель покупает платный и бесплатный билет, видит правильную сумму и QR.
- [ ] Двойной клик не создаёт два заказа; повторный checkout не дублирует билеты.
- [ ] Истёкший резерв, недостаток билетов и отказ оплаты показаны корректно.
- [ ] Кабинет показывает только доступные текущему аккаунту заказы/билеты.
- [ ] Организатор проверяет билет, повторный проход отклоняется.
- [ ] Чужие объекты, отсутствующие записи, сетевые ошибки и пустые списки обработаны.
- [ ] Основной сценарий работает на узком экране, формы имеют подписи и доступны с клавиатуры.
- [ ] `npm run build` и `npm run lint` проходят после реализации.

Проверка backend отдельно от интерфейса:

```sh
docker compose exec -T web python demo_mvp.py
```

Демо создаёт свежие записи, проверяет HTTP-сценарий и выводит IDs. Оно не выдаёт
готовые login/password для ручного входа: для работы через UI создать свои аккаунты.

В текущем MVP отсутствуют upload обложек, категории, поиск, личные данные
держателей, профильное редактирование, email verification/password reset,
возвраты, PDF, промокоды, рассадка и отдельные сотрудники check-in. Эти элементы
требуют расширения backend и не должны отображаться как работающие функции.
