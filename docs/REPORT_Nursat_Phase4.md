# Нурсат — четвёртый этап, отчёт к 29 октября

Подготовлено 29 октября 2026 года. Ветка реализации: `codex/nursat-phase4`
(от `dev`, после фронтенда #11, QR-сканера #12 и мобильного CI #4).

На этом этапе мобильное приложение Абылая и админка Мирата начинают опираться
на бэкенд всерьёз, поэтому работа шла по трём направлениям из плана:
уведомления, права Platform Admin и скорость сканирования на входе.

## Результат

- **Письмо о возврате и отмене (SRS 4.9).** После возврата платного заказа
  покупатель получает письмо: сумма возврата с пометкой «симуляция» и список
  билетов, которые больше не действуют на входе. Отмена бесплатной регистрации
  тоже присылает письмо. Письмо уходит через `transaction.on_commit`, как и
  подтверждение заказа. Повторный вызов `refund` (он идемпотентен) второго
  письма не шлёт, отмена неоплаченного резерва писем не порождает. Вместе с
  письмами о регистрации, подтверждении email и сбросе пароля (второй этап) и
  письмом о заказе (третий этап) это закрывает все уведомления из плана.
- **Приостановка пользователей и событий для Platform Admin (SRS 4.12).**
  Новые эндпоинты, пути совпадают с уже запланированными в `API_CONTRACT.md`:
  - `GET /api/admin/users?search=` — поиск пользователей с ролями и статусом;
  - `POST /api/admin/users/{id}/suspend` — `{suspended: true|false}`.
    Приостановленный пользователь не может войти, его текущий access-токен
    отклоняется на следующем запросе, refresh-токены попадают в blacklist.
    События приостановленного организатора пропадают из публичного списка.
    Platform admin нельзя приостановить через API;
  - `POST /api/admin/events/{id}/suspend` — `{suspended, reason}`. Событие
    скрывается из каталога и по прямой ссылке, кампании и Campaign QR перестают
    работать, резерв и checkout возвращают 404/409, организатор не может его
    переопубликовать, но видит событие и причину. Уже выданные билеты
    продолжают проходить check-in, чтобы не ломать вход людям, которые купили
    билеты честно. Приостановка и восстановление пишутся в журнал событий
    (audit log) с администратором как автором.
  - Новые поля события `suspended_at`, `suspension_reason` (миграция
    `0007_event_suspension`), только для чтения в обычном API. Для приостановленного
    события нельзя открыть и новое обращение в поддержку по ссылке на событие.
- **Скорость и надёжность `/tickets/verify` и `/tickets/check-in`.**
  - Check-in делал 15 SQL-запросов и блокировал строку события — ту же, что
    блокирует продажа билетов. В час пик это означало бы, что сканер на входе
    ждёт, пока завершится чужой checkout.
  - Теперь билет, событие и организатор берутся одним запросом, а сам check-in
    — один условный `UPDATE ... WHERE status = 'valid'`. Из двух одновременных
    сканов одного билета проходит ровно один (существующий тест конкурентности
    по-прежнему зелёный), событие не блокируется.
  - Verify — не более 3 запросов, check-in — не более 6. Это закреплено тестом,
    чтобы случайный N+1 не вернулся.
  - Новый скрипт `bench_checkin.py` проверяет реальный HTTP-путь так же, как
    это делает мобильное приложение: создаёт событие, выдаёт N билетов,
    назначает Event Admin и сканирует каждый билет (verify, затем check-in).

## Замер (локально, Docker, 200 билетов)

| Запрос | p50 | p95 | max |
| --- | --- | --- | --- |
| `POST /tickets/verify` | 5.1 мс | 5.7 мс | 8.3 мс |
| `POST /tickets/check-in` | 5.9 мс | 6.6 мс | 15.1 мс |
| verify + check-in | 11.1 мс | 12.4 мс | 20.1 мс |
| повторный скан (409) | 5.6 мс | | |

Цель SRS — около 2 секунд на check-in. Бэкенд занимает сотые доли от этого,
остальное — камера и сеть телефона на стороне приложения Абылая.

одно даже при повторном вызове, письмо об отмене бесплатной регистрации и его

admin; что приостановленное событие пропадает из каталога, по прямой ссылке и
по ссылке кампании, не продаётся и не переопубликуется, но билеты на нём
проходят check-in; что приостановленный пользователь теряет вход, access- и
refresh-токены и снова может войти после восстановления; что admin нельзя
приостановить; поиск пользователей; лимит SQL-запросов для verify/check-in и
отказ на повторный скан. Ruff и проверка миграций — без замечаний.

## Демо 29 октября

1. `docker compose up --build -d --wait`, затем
   `docker compose exec -T web python manage.py seed_demo`.
2. Войти как `demo-organizer@biletflow.local`, сделать возврат заказа —
   в `docker compose logs web` показать письмо о возврате.
3. Войти как `demo-admin@biletflow.local`:
   `POST /api/admin/events/{id}/suspend` с причиной — событие пропало из
   `GET /api/events`, попытка купить билет даёт 404; организатор видит
   причину в `GET /api/events/{id}` и запись в `/audit-log`.
4. Тот же admin приостанавливает `demo-attendee` — его токен сразу
   перестаёт работать (`GET /api/auth/me` → 401), вход отклоняется.
5. `docker compose exec -T web python bench_checkin.py` — таблица задержек
   сканера; затем скан билета мобильным приложением Абылая.
