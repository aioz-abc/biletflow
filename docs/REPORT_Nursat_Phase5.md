# Нурсат — пятый этап, отчёт к 12 ноября

Подготовлено 12 ноября 2026 года. Ветка реализации: `codex/nursat-phase5`
(от `dev` после Phase 4 Мирата, PR #21).

Пятый этап — интеграция. Цель из плана: свежий `git clone` +
`docker compose up` даёт рабочее демо целиком, а бэкенд отдаёт всё, что нужно
дашборду Мирата. Заодно закрыты два хвоста Phase 4: активация платных продаж
(SRS 4.5) и данные посетителя на билете (SRS 4.6, 4.7).

## Результат

- **Аналитика события `GET /api/events/{id}/analytics` (SRS 4.15).**
  Реализован контракт из `docs/ANALYTICS_REQUIREMENTS.md`, согласованный
  Миратом и Айжан в PR #19:
  - фильтры `from`/`to` — календарные дни по Алматы (`to` не включается),
    максимум 366 дней, плюс необязательный `ticket_type`; ошибки → 400;
  - продажа, скидка, сбор и выпущенные билеты считаются в день подтверждения
    заказа, возврат и отмена сбора — в день возврата;
  - `totals`, ряд `daily` за каждый день интервала (с нулевыми днями), строки по
    типам билетов и по кампаниям; суммы по дням и по типам сходятся с
    итогами точно, до тиына, а за всё время совпадают со сводкой `/sales`;
  - `inventory` — текущий снимок (`as_of`): вместимость, активные и
    зарезервированные билеты, остаток, процент check-in. С фильтром по типу
    квота типа (`type_remaining`) идёт отдельно и никогда не подменяет
    вместимость события;
  - скидка по строкам берётся из `OrderItem.discount_minor` (PR #20 Айжан),
    сбор делится между строками заказа пропорционально оплаченной сумме тем
    же правилом округления (вынесено в общую `split_by_weight`).
  Все 10 сценариев приёмки из требований покрыты тестами (`test_analytics.py`).
- **Активация платных продаж (SRS 4.5, UC2).**
  - Платные билеты события нельзя зарезервировать и оплатить, пока организатор
    не прошёл чеклист: платный тип билета, проверка личности, платёжный
    аккаунт, принятие условий, оплата сбора активации (5 000 KZT). Всё это
    симуляция, без реальных данных и денег. Бесплатные билеты не затронуты.
  - `GET/POST /api/events/{id}/activation` — чеклист и шаги; сбор можно
    оплатить только после остальных шагов, повторная оплата ничего не меняет;
    номер, похожий на настоящий счёт или карту, отклоняется.
  - Активация действует только на выбранное событие.
  - Platform admin: `GET /api/admin/activations` и
    `POST /api/admin/activations/{id}/suspend` — остановить или вернуть платные
    продажи при подозрении на мошенничество. Проверка повторяется и при
    оплате, так что уже созданный резерв после приостановки не оплатить.
  - Каждый шаг пишется в журнал события.
- **Посетитель на билете (SRS 4.6, 4.7).** При оплате можно указать имя
  (и email) для каждого билета; пустые билеты оформляются на покупателя. Имя
  видно на странице билета, в письме, в PDF-билете Мирата, в списке
  посетителей организатора и при сканировании на входе. Покупатель может
  передать действующий билет другому человеку (`PATCH /api/tickets/{id}`).
  Старые билеты миграция заполнила данными покупателя.
- **Фронтенд в Docker Compose.** Новый сервис `frontend` (Vite) рядом с `db`
  и `web`: одна команда поднимает всё, приложение на `localhost:5173`,
  `/api` и ссылки Campaign QR `/c/` проксируются в бэкенд. Исправлено:
  ссылки Campaign QR раньше строились от адреса прокси и в Docker вели бы на
  недоступный `web:8000`.
- **Экраны во фронтенде:** страница «Paid sales activation» в кабинете
  организатора, баннер на странице продаж события, поля «Name on each ticket»
  при оплате, имя владельца на странице билета.
- `seed_demo` и `demo_mvp.py` проходят настоящую активацию; `demo_mvp.py`
  дополнительно сверяет аналитику с `/sales`.

## Интеграция с мобильным приложением — передать Абылаю

По плану этот этап связывает бэкенд, фронтенд и мобильное приложение. Сам
код `mobile/` — зона Абылая, поэтому здесь только найденные расхождения с API:

- вход отправляет `{username, password}`, а `POST /api/auth/login` принимает
  `{email, password}` и на лишнее поле отвечает 400 — войти сейчас нельзя;
- токен `access` из ответа не сохраняется, список событий захардкожен;
- отсканированный код только показывается, а не отправляется в
  `POST /api/tickets/verify` и `POST /api/tickets/check-in` (тело
  `{qr_token}`; повторный скан → 409; ответ содержит `attendee_name`).

## Проверка

```sh
docker compose up --build -d --wait     # db, web и frontend
docker compose exec -T web python manage.py test --noinput
docker compose exec -T web sh -c "ruff check . && ruff format --check ."
docker compose exec -T web python manage.py makemigrations --check --dry-run
docker compose exec -T web python demo_mvp.py
cd frontend && npm test && npm run lint && npm run build
```

Бэкенд: **121 тест** (было 87 на прошлом отчёте; новые — аналитика, активация,
посетители, а также тесты из PR Айжан), все проходят на PostgreSQL 16.
Фронтенд: **48 тестов**, lint и сборка без замечаний. Сканер после изменений:
verify + check-in — 12 мс p50 / 14 мс p95 (`bench_checkin.py`).

Весь путь пройден в браузере против Docker Compose: организатор создаёт платное
событие, видит баннер, проходит чеклист (номер карты в поле платёжного
аккаунта отклоняется), оплачивает симулированный сбор; посетитель покупает два
билета, один на другое имя, и получает их с именами владельцев.
Проверка свежего клона описана в PR.

## Демо 12 ноября

1. `git clone` → `docker compose up --build -d --wait` →
   `docker compose exec -T web python manage.py seed_demo`; открыть
   `localhost:5173`.
2. Войти как `demo-organizer@biletflow.local`, создать платное событие —
   на странице продаж баннер «Paid tickets cannot be bought…». Пройти
   «Paid sales» до статуса «Paid sales active».
3. Войти как `demo-attendee@biletflow.local`, купить два билета, вписать имя на
   второй — на странице билета виден владелец, в `docker compose logs web` —
   письмо с именами.
4. `GET /api/events/{id}/analytics?from=…&to=…` от организатора — итоги, ряд
   по дням и строки по типам; сравнить с `/sales`.
5. Войти в `localhost:5173/admin` как `demo-admin@biletflow.local` и через API
   приостановить платные продажи (`/api/admin/activations/{id}/suspend`) —
   покупка платного билета даёт 409, бесплатные продолжают работать.
